# Cohorts and retention

Read this when: deciding what "active" means, building retention curves, judging whether
retention is good, tracking churn and net revenue retention by cohort, comparing retention
across channels, plans or personas, or explaining why growth stalled despite steady signups.

## Define "active" by value, not presence

An active user or account is one that performed the core value action in the period. Logging
in, opening the app, or loading a dashboard is presence; a metric built on presence rises with
notification emails and falls with nothing the product controls.

| Product type | Active means | Natural period |
|---|---|---|
| Daily work tool (chat, issue tracker) | created or changed a core object | day or week |
| Weekly workflow (reporting, planning) | completed the workflow (report generated, plan published) | week |
| Monthly or event-driven (invoicing, payroll, tax) | completed the job | month, or per occurrence |
| API or infrastructure | made successful production API calls above a floor | week or month |
| Automation that runs unattended | the automation ran and delivered output | week; no human session is expected |
| Marketplace | completed a transaction (each side counted separately) | depends on purchase cycle |

Rules:

- **Match the period to the natural frequency of the problem.** Measuring a monthly-use product
  with daily actives produces a number that looks terrible and means nothing. Find the natural
  frequency from the median gap between core actions among retained users.
- **Passive value counts.** A monitoring tool whose user never logs in because nothing broke is
  delivering value. Count delivered outputs (alerts sent, reports emailed and opened, jobs run)
  as activity when the product works without a session.
- **Unit**: account for B2B, with user-level activity as a depth measure inside it. An account
  with one active seat out of twenty is active and at risk at once.
- **Exclude** internal users, test accounts, and activity generated by the team's own
  impersonation or by seeded demo data.
- Write the definition once in the metric dictionary (`references/north-star-metrics.md`).
  Changing it later re-bases every historical chart; restate history when it changes.

## Cohort retention curves

Stage: at Prototype, list who came back, by name. Curves start at Launch, with monthly cohorts
while weekly ones are too small to read.

A cohort is the set of units that started in the same period (signup week or month, or first
payment month for revenue). The curve plots the share of the cohort active in each later
period. Three variants give different numbers from the same data, so name the one in use:

| Variant | Counts a unit as retained in period N if | Use |
|---|---|---|
| Classic (N-period) | active exactly in period N | default for product usage |
| Unbounded (rolling) | active in period N or any later one | infrequent products; always looks higher, and recent periods are not yet final |
| Bracket | active within a custom range (day 1, days 2–7, days 8–30) | consumer apps with decaying frequency |

A minimal classic weekly table in SQL (analysis at depth belongs to the `data` skill):

```sql
-- date_trunc on timestamptz uses the session time zone: run with SET TIME ZONE 'UTC'.
with cohort as (
  select id as user_id, date_trunc('week', created_at)::date as cohort_week
  from users
),
activity as (
  select distinct user_id, date_trunc('week', occurred_at)::date as active_week
  from events
  where name = 'report_published'
)
select c.cohort_week,
       (a.active_week - c.cohort_week) / 7 as week_n,  -- date minus date is integer days
       count(*) as active_users
from cohort c
join activity a using (user_id)
where a.active_week >= c.cohort_week
group by 1, 2
order by 1, 2;
```

Divide by cohort size (count from `cohort`, not from the join, so cohorts with zero activity
keep their denominator). For B2B, key both CTEs on the account ID instead of the user ID.

Reading the curve:

- **Shape matters more than level.** A curve that flattens to a horizontal line means a set of
  users found lasting value; the plateau height is the retained share. A curve that keeps
  sloping toward zero means no durable value yet, and acquisition spend only fills a leaking
  bucket. A curve that rises after its low point (a "smile") means resurrection or expansion.
- **Find where it flattens**: the period after which period-over-period loss becomes small
  (rule of thumb: under about one percentage point per period, sustained). Everything before
  that point is the onboarding and early-habit problem; everything after is the base the
  business is built on.
- **Compare cohorts over calendar time.** Newer cohorts' curves sitting above older ones at the
  same age is the clearest evidence that the product is improving. Overlay cohorts on the same
  age axis; do not average all cohorts into one curve, which hides the trend and over-weights
  old cohorts at long ages.
- **Mask incomplete periods.** The most recent cell of each cohort covers a partial period and
  always reads low. Exclude the current period.
- **Small cohorts are noise.** In a cohort of 40, one user is 2.5 points. Pool weekly cohorts
  into monthly ones until each cohort has roughly 100+ units, and do not react to a single
  cohort's wobble.
- **Period 0 is 100% by construction** only if the cohort is defined by the active event. If
  cohorts are defined by signup and activity by a core action, period 0 shows the activation
  gap; state which.

"Is retention good?" has no universal number: it depends on product category, price, customer
size and natural frequency, and published benchmarks vary too widely to quote. Answer with the
three things that can be established from the product's own data: does the curve flatten at
all, is the plateau rising for newer cohorts, and does the plateau times expected lifetime
revenue cover acquisition cost (`0x:pricing-monetization` for unit economics).

## Logo churn and net revenue retention

Usage retention predicts revenue retention; revenue retention is what the business lives on.
Track both, by cohort of first payment month.

| Metric | Formula over a period, for customers paying at its start | Notes |
|---|---|---|
| Logo churn | customers lost ÷ customers at start | counts accounts; a small and a large customer weigh the same |
| Gross revenue retention (GRR) | (starting MRR − contraction − churned MRR) ÷ starting MRR | cannot exceed 100% |
| Net revenue retention (NRR) | (starting MRR + expansion − contraction − churned MRR) ÷ starting MRR | can exceed 100%; excludes new customers |

Cohort view: for customers whose first payment fell in month M, logo retention at month M+n
is the share still paying, cohort NRR is that cohort's MRR at M+n ÷ its MRR at M, and cohort
GRR is the same with each customer's MRR capped at its starting value. A cohort NRR line that
bends back up means expansion outruns churn; newer cohorts' lines sitting above older ones at
the same age mean the product or the customer mix improved. Pool months into quarters while a
monthly cohort holds only a handful of customers.

Traps:

- **Monthly churn compounds.** 3% monthly logo churn loses about 31% of customers in a year;
  5% loses about 46%. Convert before judging: annual = 1 − (1 − monthly)^12.
- **NRR hides churn.** A few expanding accounts can lift NRR above 100% while many small ones
  leave. Always show GRR and logo churn beside it.
- **Annual plans delay the signal.** Customers on annual contracts cannot churn until renewal;
  a blended monthly churn rate looks good until the first renewal wave. Compute churn against
  customers **up for renewal** in the period, and report monthly and annual plans separately.
- **Voluntary vs involuntary.** Failed payments are a billing problem with a different fix
  (dunning, card updater; see `0x:payments-billing`). Split churn by reason at the source.
- **Date conventions** change the number: cancellation requested vs access ended, and whether
  a pause, a downgrade to free, or a reactivation within N days counts as churn. Decide once
  and write it down.
- **Early cohorts differ.** The first customers came through the founder's network and
  behave unlike later ones; do not forecast from them alone.
- MRR itself, and anything reported to investors, comes from the billing system and is owned by
  `0x:startup-finance`; this file covers the cohort view.

Small numbers: with fewer than about 50 paying customers (rule of thumb), a monthly churn
percentage is not a statistic. Keep a list of every churned customer with the reason, tenure, plan and channel,
and read the list.

## Segment retention

Average retention blends groups with very different curves, and the best growth decision is
usually to shift acquisition toward the group that already retains.

| Segment by | What to look for | Action |
|---|---|---|
| Acquisition channel (first touch) | channels with cheap signups and a curve that goes to zero | judge channels on retained or paying customers, not signups (`references/attribution.md`) |
| Plan and billing interval | free vs paid; monthly vs annual; a plan whose users never reach the gated value | fix packaging (`0x:pricing-monetization`) |
| Persona, role, company size | one segment plateaus high while the rest decay | that segment is the real market; narrow positioning toward it |
| Activated vs not | large gap confirms the activation definition | if the gap is small, the activation event is wrong |
| Signup cohort | newer vs older | did product changes help |
| Team size or seats used | single-seat accounts churn more in collaborative products | invite prompts, multiplayer value |

Guard against two errors. First, segments defined by behavior after signup (activated, used
feature X) describe correlation, not cause (`references/funnels-activation.md`). Second, a
shift in mix moves the blended curve without any segment changing: when blended retention
drops, check the channel and plan mix of recent cohorts before blaming the product.

## Engagement depth

Retention is binary (came back or not). Depth distinguishes an account about to churn from one
that is embedded.

- **Frequency**: distribution of active days per user in the last 28 days (an "L28" histogram),
  or active weeks in the last 12. Look at the distribution, not the mean. A healthy
  habit product shows a second hump at high frequency; a single spike at 1–2 days means most
  "actives" are barely there. Define a **power user** threshold from this histogram.
- **Stickiness**: DAU ÷ MAU, the average share of monthly actives present on a given day. Only
  meaningful for products with daily natural frequency; for weekly products use WAU ÷ MAU.
  Do not set a target on a ratio whose denominator can be shrunk by losing casual users.
- **Breadth**: number of distinct core features or use cases an account uses, and in B2B the
  share of seats active. Accounts using several features or integrations usually churn less,
  but that can be switching cost or simply a marker of fit: a hypothesis to test, not a
  proven lever.
- **Intensity**: volume of the value unit per active account (documents, API calls, minutes).
  This is also the input to usage pricing.
- An **account health score** is a rule over these (for example: active in 3 of the last 4
  weeks, 2+ features, 50%+ seats active). Keep it to a few transparent rules; validate it by
  checking that last quarter's churned accounts scored low before they left. Skip it until
  there are enough paying accounts for it to change who gets contacted.

## Growth accounting

Net change in actives hides four flows. For each period, classify every unit that was ever
active:

| State | Definition |
|---|---|
| New | active this period, first time ever |
| Retained | active this period and the previous one |
| Resurrected | active this period, not the previous one, but active earlier |
| Churned | active the previous period, not this one |

Identity: actives(t) = new + retained + resurrected, and
actives(t) − actives(t−1) = new + resurrected − churned.

- **Quick ratio** = (new + resurrected) ÷ churned. Above 1 the active base grows; a ratio that
  is high only because new users are high, with churned close behind, is growth that stops the
  moment acquisition slows.
- Plot the four flows as a stacked bar per period with churned below zero. Flat totals with
  large new and large churned bars is the leaky-bucket picture; fixing retention is worth more
  than more acquisition.
- Rising resurrection after a re-engagement campaign is real only if those users are retained
  the following period; otherwise the campaign rents activity.
- The same decomposition applies to revenue: new, expansion, resurrected, contraction and
  churned MRR per month.
- Choose the period by natural frequency. With too short a period, normal gaps between uses
  appear as churn followed by resurrection, and both flows are inflated.

## Ask the user

- **How often should a happy customer use the product?** Sets the period for every retention
  metric. Default: weekly for B2B tools; derive it from retained users' median gap when data
  exists.
- **Which action means the customer got value?** Defines active. Default: the completed core
  action used in the activation definition.
- **When does a customer count as churned (cancel request, end of paid period, downgrade to
  free, pause)?** Changes churn and NRR. Default: at the end of the paid period; downgrade to
  free is logo churn for revenue metrics and still active for usage metrics.
- **Are there annual contracts?** Requires renewal-based churn. Default: report monthly and
  annual plans separately.
- **Which customer segment is the business trying to win?** Decides whose curve matters when
  segments diverge. Default: the segment with the highest plateau and enough volume.
